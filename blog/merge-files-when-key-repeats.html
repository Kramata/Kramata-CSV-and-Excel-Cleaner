Merging files when a key repeats (and why VLOOKUP picks the wrong row)

Updated November 8, 2026

Two ways a repeated key quietly damages a merge, and how to avoid both.

Short answer: a repeated key forces a choice, and most tools make it without telling you. VLOOKUP takes the first row it finds. Joins keep every match and add rows. Decide which row should win, keep your row count fixed, and make sure something reports the repeats, including on next month’s file.

What a repeated key looks like

You have orders, and you want each customer’s city from a second file. Customer C1 moved, so the customer export has two rows for them:

IDCityRow
C1Old town2
C2Riverside3
C1New town4

One order, two possible cities. There are only three things a tool can do: take one row, take both, or stop and ask. The damage comes from the tools that do one of these without saying so.

Why VLOOKUP picks the wrong row

With an exact match, VLOOKUP reads from the top and stops at the first hit. For C1 that’s Old town. There’s no error and no hint that a second row exists. It isn’t a bug: the first row is simply what it returns. But exports are often in date order, so the first row is the oldest one, and the record you wanted is further down.

The approximate-match form is worse here. If the last argument is TRUE or left out, VLOOKUP assumes the column is sorted, and on unsorted data it can return an unrelated row, again with no error.

XLOOKUP gives you the choice: set search_mode to -1 and it searches from the bottom up. You still aren’t told that the key repeated.

The opposite failure: joins that add rows

Power Query’s Merge, pandas merge and SQL joins take the other route and return one row per match. The order for C1 becomes two orders. Nothing looks broken until a total comes out too high, because that order is now counted twice.

How to do it safely

  1. Check for repeats first. In Excel, =COUNTIF(A:A,A2)>1 beside the lookup column marks them.
  2. Decide which row should win. Usually the newest. If the file isn’t in date order, sort it first so that “first” or “last” means what you want.
  3. Reduce the lookup table to one row per key, then merge. This is what keeps the row count fixed.
  4. Compare row counts before and after. Same number in and out means nothing multiplied.

In pandas, you can make the merge fail if a repeat gets through:

lookup = customers.drop_duplicates(subset="ID", keep="last")
result = orders.merge(lookup, left_on="Cust", right_on="ID",
                      how="left", validate="many_to_one")

Keys that almost match

The reverse problem is a key that should match and doesn’t: C3 against C3 with a trailing space. VLOOKUP ignores case but not spaces, so that row comes back as #N/A. Excel’s TRIM fixes ordinary spaces, but not the non-breaking spaces that often arrive from web exports.

Be careful about fixing this automatically. In some systems ABC and abc are different codes, and a tool that quietly folds them together attaches the wrong record, which is the same problem you started with.

That last row matters most. A recipe can be clean the week you build it, and next week’s export can contain a duplicate nobody expected.

What it doesn’t do: it can only choose the first or last row in the file’s order, so if you want the row with the latest date, the other file needs to be in date order first. It also won’t bring in every match, because that would change your row count.

FAQ

Why does VLOOKUP return the wrong row when there are duplicates? With an exact match, VLOOKUP stops at the first matching row from the top and gives no sign that others exist. If the row you wanted is further down, such as the newest record in an export, you get the older one.

How do I get the last match instead of the first? In Excel, use XLOOKUP with search_mode set to -1, which searches from the bottom up. In pandas, use drop_duplicates with keep="last" on the lookup table before merging. In Kramata, set the merge step to Use last row.

Why did my row count go up after a merge? A key repeated in the lookup file, and the tool created one output row for every match. Power Query, pandas and SQL joins all do this unless you remove the duplicates from the lookup table first.

Does Kramata change my row count when a key repeats? No. Kramata uses one row per key from the other file, so with Keep all rows you get the same number of rows out as you put in. It tells you how many keys repeated and which row it used. The Only matches setting removes rows that found no match, and Kramata reports how many.

Should I ignore case and spaces when matching keys? Only if you know those differences don't mean anything in your data. In some systems ABC and abc are different codes. Kramata matches exactly by default, tells you how many unmatched rows differ only by case or spaces, and leaves the choice to you.
